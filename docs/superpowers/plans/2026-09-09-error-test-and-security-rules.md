# Error, Test, and Security Rules Implementation Plan (version one, plan 3 of 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the rest of spec 4.1: `swallowed-error`, `test-no-assert`, `test-newly-skipped`, and the security pack (`secret-exposed`, `weak-crypto`, `injection-sink`, `html-injection`, `vulnerable-dependency`, the two Supabase rules, the three Express rules), each with must-flag / must-not-flag / edge fixtures and a precision check on the founder's repositories.

**Architecture:** Part A (branch `engine/erosion`) adds what the erosion and test rules need: a `[framework]` config section, `root`, `offline`, and a `Previous` snapshot on `RuleContext`, a shared test-case extractor in core, a `skipped_tests` index table so `--changed` and diff scopes can tell "newly skipped" from "already skipped", and three rules. Part B (branch `engine/security`) adds the security pack: a secret pattern table with an entropy check and a Supabase JWT role decoder, three AST rules, lockfile parsers and an OSV client with an on-disk cache (the engine's first and only network call, off under `--offline` or on any failure, never blocking on the network), and the framework rules. Every rule is a pure function over `RuleContext`; the two rules that must read non-source files (`supabase-table-without-rls` reads SQL migrations, `vulnerable-dependency` reads a lockfile) do so through `ctx.root`, which is the one documented exception to "rules never touch the filesystem".

**Tech Stack:** Rust 2021, tree-sitter 0.23, rusqlite 0.32, blake3, serde, toml, globset, rayon, clap 4 (all present). New: `regex = "1"` (secret patterns), `ureq = { version = "2", features = ["json"] }` (OSV), `base64 = "0.22"` (JWT payload decode). Tests are `#[test]` functions over fixture directories.

**Spec:** `docs/superpowers/specs/2026-09-05-agent-native-quality-gate-design.md`, sections 4.1 (the eleven rule lines this plan implements, with their OWASP and CWE ids), 4.3 (blocking policy; `secret-exposed` always blocks and cannot be downgraded), 7.1 (`owasp` and `cwe` on findings), 7.5 (`framework hints`, `blocking policy`), 9 (OSV unreachable: cached snapshot with age warning, else skip with a warning, never block on network), 10.1 and 10.2 (fixtures per rule, 85 percent precision gate). Plans 1 and 2 are the code this builds on; read `crates/rules/src/lib.rs`, `crates/cli/src/run.rs`, and `crates/core/src/index.rs` before Task 1.

**What this plan does not do.** `init`, hooks, and the MCP server are plan 4. Cross-function and cross-file taint, `test-mock-only`, and the framework packs for Next.js, Expo, and Laravel are release two (spec 4.2). PHP and Python are phase two.

## Global Constraints

- Product name Locrin; config `locrin.toml` (`core::config::CONFIG_FILE`); baseline `locrin-baseline.json`. Cache directory from `core::index::cache_path`'s parent (`<cache>/locrin/<repo key>/`).
- No LLM anywhere. Network access exists in exactly one place, `core::osv::fetch`, used only by `vulnerable-dependency`, only when a lockfile exists, and never under `--offline`; every network failure degrades to the cached snapshot or to a warning, never to exit 1 or exit 2 (spec 9).
- Rule contract as of plan 2 Part B: `Rule: Sync` with `id`, `description`, `scope`, `category`, `default_severity`, `confidence`, `enabled_by_default`, `run -> anyhow::Result<Vec<Finding>>`; `RuleContext { files, config, index: Option<&Index>, entries }` (Task 1 adds `root`, `offline`, `previous`). `finding_at(rule, rel, span, anchor, evidence, fix)` builds every finding; `owasp` and `cwe` are set by the rule after construction. Ids stay `blake3(rule + "\x1f" + rel + "\x1f" + anchor)[..16]`.
- New rules and defaults (category Security unless stated):
  - `swallowed-error` (Erosion): severity Medium; confidence High for an empty catch and a floating promise, Medium for a log-only catch.
  - `test-no-assert` (Erosion): severity Low, confidence Medium.
  - `test-newly-skipped` (Erosion): severity Medium, confidence High.
  - `secret-exposed`: severity High, confidence High, `locked() == true` (config cannot lower its severity or disable it). OWASP `A02:2021`, CWE `CWE-798`.
  - `weak-crypto`: severity High; confidence High when the credential context is explicit, Medium otherwise. `A02:2021`, `CWE-327` (MD5, SHA-1, static IV) or `CWE-338` (Math.random).
  - `injection-sink`: severity High; confidence High for eval/new Function with any non-literal and for template or concatenated command and SQL strings, Medium for a bare identifier reaching a SQL sink. `A03:2021`, `CWE-95` / `CWE-78` / `CWE-89`.
  - `html-injection`: severity High, confidence Medium. `A03:2021`, `CWE-79`.
  - `vulnerable-dependency`: severity from the advisory (CRITICAL or HIGH to High, MODERATE to Medium, LOW or unknown to Low); confidence High when the advisory names a fixed version and its severity is High, Medium otherwise. `A06:2021`, `CWE-1395`.
  - `supabase-service-role-in-client`: High / High. `A01:2021`, `CWE-284`.
  - `supabase-table-without-rls`: High / High. `A01:2021`, `CWE-284`.
  - `express-route-without-auth`: High / High, runs only when `framework.auth_middleware` is non-empty. `A01:2021`, `CWE-306`.
  - `express-cors-wildcard-on-authenticated`: High / High. `A05:2021`, `CWE-942` (the spec lists 306 and 614 for the Express group; 942 is the accurate id for a permissive cross-domain policy and is recorded here as a deviation).
  - `express-cookie-insecure`: High / High. `A05:2021`, `CWE-614` (missing `secure`) or `CWE-1004` (missing `httpOnly`).
- Precision gate (spec 10.2, plan 2 precedent): each measurable rule is sampled 20 findings on the corpus (FastLift, StrongSpan, teyji, autoqa, fastlift-admin; whichever produce findings). Under 17/20 the rule ships `enabled_by_default() == false` with the reason in its doc comment and in the precision report. A rule that produces no findings on the corpus is unmeasured and ships on fixture evidence, stated as such. `secret-exposed` is the exception: it is `locked`, so a miss there STOPS for the founder.
- Evidence never contains a secret: `secret-exposed` prints the provider and a mask (first four characters, an ellipsis spelled `...`, the length).
- Schema bumps once, to `"4"`, in Task 3 (`skipped_tests`, `osv_batch`, `osv_vulns`); spec 9 rebuilds on mismatch.
- Performance targets stay tests (cold under 5 s, warm single-file under 300 ms, warm 30-file under 1 s, startup under 50 ms); the security rules are file rules and run in the parallel pass; `vulnerable-dependency` is a graph rule that runs every run and must cost under 50 ms warm (cached), measured in Task 16.
- Git: Part A on `engine/erosion` off `main`; Part B on `engine/security` off `main` after A merges (stacked if A is in review). One commit per task, `cargo fmt --all` before every commit, plain `engine: ...` messages, no attribution trailers, never `git add -A`. No em dashes anywhere.
- `export PATH="$HOME/.cargo/bin:$PATH"` before any cargo command. Corpus checkouts: the FastLift checkout, the StrongSpan checkout, the Teyji checkout, the autoQA checkout, the FastLift admin checkout. Never write into them; use a fresh `LOCRIN_CACHE_DIR` per measurement.
- Expected fixture line numbers were counted by hand; if a test fails only on a line number, recount against the fixture before touching the rule.

## Deviations recorded during execution

(Empty at planning time. The executor appends every ruling here with its reason, as plan 2 did.)

- **Task 1, `framework.server_paths` is validated at config load.** The task did not ask for it. `config::validate_globs` carries the invariant that every glob in every list is validated there, so a bad pattern fails the run at the config rather than being silently dropped by whichever consumer happens to compile it; `server_paths` is a glob list a Part B rule will compile, so it joins the list with a test (`an_invalid_server_path_glob_is_an_error`). `auth_middleware` holds identifiers rather than globs and is not validated.

- **Task 1, `rule_runs` extracted, and the CLI's findings-cache key uses it.** The task puts locking inside `run_rules`. `crates/cli/src/run.rs` decides independently which file rules the findings cache is keyed on, so left alone a repository with `[rules.secret-exposed] enabled = false` would have dropped a locked rule from the cache key while `run_rules` still produced its findings, and a file served from the cache would have been reported without them. `rule_runs(rule, config)` is now the single place the enablement decision is made and both callers ask it.

- **Task 1, `run_file_rules` unpacks the base context before the rayon closure.** `RuleContext { ..*base }` inside the closure does not compile: the base's `Option<&Index>` makes the whole context non-`Sync` even though every per-file context sets `index: None`. The five fields that actually cross the pool are unpacked by name instead, which is also explicit about what does.

- **Task 3, the git source reads only test files.** The plan says a diff scope runs `show_at` and `parse_source` over *each* scope file. `Previous` holds nothing but `skipped_tests`, so for a file that is not a test file both paths produce the empty set, and reading the rest would fetch and parse every changed file a second time (they are all parsed at HEAD by the same run) to learn nothing: on a large pull request that doubles the parse cost of the `--base` gate. `run::skipped_at` therefore returns early for a non-test path, and its doc comment says that a later field needing the whole previous file widens it. Observably identical for every rule in this plan.

- **Task 4, the floating-promise fixture line numbers were recounted.** The task expected the two floating-promise findings in `flag/a.ts` at lines 27 and 28. Counted against the fixture the task itself gives verbatim, `refresh();` is line 28 and `loadConfig("y");` is line 29 (the fixture starts at the task's line 13, so task line N maps to fixture line N minus 12). The empty catch at 6 and the log-only catch at 13 were right. The assertions use the recounted lines and the fixture was not touched; Global Constraints line 40 authorises this outright.

- **Task 4, the member-call floating-promise arm fires only through `this`.** The task allowed `<obj>.<name>(...)` to match any same-file async function or method. Smoked over strongspan that flagged `renderer.unmount();` in `src/__tests__/volumeParity.test.tsx`, a React test renderer method that happens to share a name with the file's own `async function unmount` two lines above: one file's syntax cannot say what `renderer` is. The rule now keeps two sets of async names, functions and arrows for identifier callees and methods for member callees, and accepts a member callee only when its object is `this`, the one object a single file resolves. A consequence is that the task's separate `SETTLERS` guard against a call followed by `.then(` / `.catch(` / `.finally(` became structural (the object of a settled promise is a call expression, not `this`) and was deleted for a comment saying why it is unnecessary. This narrows what the rule reports and never widens it, with a reproduced false positive behind it.

- **Task 7b, the skipped-case extraction moved into the parallel parse pass, through a new `testcases::skipped_names`.** The controller's ruling was to compute the names in the pool closure and pass them to `indexer::record_with_stat`, with the other call sites computing them inline. Four places would then have held the same three lines (the `is_test_file` guard, the extract, the filter to skipped names), and the guard is a correctness rule rather than a convenience: a file that stops being a test file must have its stored set cleared, so a caller that forgot the guard would leave a stale set behind and the rule would then answer from it. `testcases::skipped_names(file)` is the one place it lives, and the CLI's parse closure, the two repair-pass call sites and the rules-crate test helper all call it. `record` grew the same parameter for the same reason. Measured effect on the cold benchmark: 7037 to 7583 ms becomes 5152 to 5983 ms.

- **Task 7b, `swallowed-error` form 1 now fires only on a catch body with no children at all.** Task 4 chose the opposite, and its module doc argued the case: a comment does not make a failure visible at runtime, and a repository that means it writes `locrin:allow`. The corpus overruled it. 89 of the rule's 100 findings across the five repositories were a catch whose body is a comment saying the swallow is deliberate and naming what happens instead, and not one catch empty of everything existed anywhere in 2674 files; on a mature repository the rule was asking, at a blocking severity, for ninety decisions to be annotated that had already been made and written down. The edge fixture leg that pinned the old behaviour is flipped and a new pair pins that a comment-only body is not read as log-only either (`all` over no statements is vacuously true, so form 2 needed an explicit guard).

- **Task 7b, `test-no-assert` counts Testing Library throwing queries as assertions.** The rule's module doc named the custom matcher as a deliberate blind spot, on the reasoning that guessing which calls are matchers would flag nothing. `getBy*`, `getAllBy*`, `findBy*` and `findAllBy*` are not a guess: they throw (or reject) when they find nothing, which is what an assertion is, and all 20 findings in the first precision sample were that shape. `queryBy*` is excluded because it returns null. Both spellings count, the bare call and the member call, the second read off the property because `within(row).getByRole(...)` has no leftmost identifier to recognise. This narrows what the rule reports and never widens it. The `extracts_every_case_form...` unit test's count for one case moves from 1 to 2, because a `getByText` nested inside an `expect` is now counted on its own; rules only ask whether a case asserts at all, so the double count is harmless.

- **Task 7b, the corpus was re-measured on a binary with the two rules re-enabled.** Both ship `enabled_by_default() == false` since Task 7, and neither the CLI nor the corpus offers a way to turn a rule on without writing a `locrin.toml` into the repository, which the task forbids. The measurement binary flips those two methods and is discarded; nothing else differs from the commit under measurement. The first measurement did not need this because it ran at `9edaf4f`, before the default change.

- **Task 7c, `swallowed-error` form 2 asks whether a caller reads a value back, not where the call sits.** Task 4 read "the caller uses the result" as "the call's parent is not an expression statement", which is true of `await f()`, `void f()` and `f().finally(g)` alike. Every spelling a `Promise<void>` function is called by has such a parent, so a void async function whose catch logs was reported as soon as its file called it at all: all six of the rule's form 2 findings across the five repositories were that, and Task 7b labelled every one false. The check now climbs the wrappers that read nothing off a call (`await`, `void`, parentheses) and the chain a settled promise puts around it, and asks what the outermost one sits in; an expression statement is the answer "the value went nowhere". Binding an awaited call is still a use and a new flag fixture pair pins it. This narrows what the rule reports and never widens it. Form 2 now finds nothing on 2674 indexed files.

- **Task 7c, `test-no-assert` counts a `throw` statement as an assertion.** All 11 of the rule's remaining findings were a guard case walking a data set and calling `throw new Error(...)` with a written explanation when an invariant broke. A runner reports a thrown error as a failed case, so those check exactly what an `expect` would; they just name no matcher, and the per-item loop is where the style pays off because the message can name the item. A `throw_statement` anywhere in a case body counts, nested blocks and loops included, and a same-file helper whose own body throws becomes an assertion helper on the same one level the `expect` helpers get. The cost is pinned in the unit test rather than assumed: a case that catches its own call and rethrows reads as asserting, because separating that from a guard needs to know whether the try body can fail. The rule found nothing at all on the corpus afterwards.

- **Task 7c, `test-no-assert` ships on by default again.** Global Constraints: a rule that produces no findings on the corpus is unmeasured and ships on fixture evidence, stated as such. It produces none across 2674 indexed files, and both classes it lost over Tasks 7b and 7c were its own blind spots rather than the corpus's style, so the `enabled_by_default` override is deleted and its three tests run on `Config::default()` instead of `rule_on("test-no-assert")`. `swallowed-error` keeps the override: its five remaining findings were all labelled and none is true.

- **Task 7c, the first cold benchmark run of a session is discarded and reported.** The cold benchmark reads all 1846 files of the bench checkout, so the first run after a long gap measures the operating system's page cache rather than the engine: 6602 ms, with warm numbers on the same invocation faster than any Task 7b recorded. The three runs after it are 3750, 3790 and 3764 ms, all green, on a machine confirmed idle beforehand. All four numbers are in the report. Task 7c changed no indexing code, so the 5152-to-3764 ms move confirms Task 7b's reading that the 152 ms it could not close was the measuring box; the target was not touched.

- **Task 3, an unchanged file the run parsed gets a `previous` entry from the index (26cbeea).** The pipeline rule put the capture inside the changed branch, so "everything else has no entry" swept up two sets of files the rules do see: the file a named path scopes to, which is usually unchanged because the developer is asking about a file rather than reporting an edit, and any file a full run could not serve from the findings cache. Both reach the parser, and `test-newly-skipped` read them as files with no history and reported every legacy skip in them on every check. The index's stored set for such a file *is* its previous version, because nothing has edited it, so the capture now runs for any candidate that reached the parser and had a `files` row. The repair pass inserts the same entry for the same reason (1a7389c): it puts an unchanged importer into `files` and the rules then run over it. The rule is narrowed to "files served from the cache and files never indexed have no entry", and the Task 3 pipeline text is corrected to match. A file the index has never seen still has no entry, so the documented first-run behaviour is unchanged.

- **Task 4, form 2 inside a `method_definition` judges use through `this.<name>()` callers only (6d0cc27).** The task's check asked whether the enclosing function's name is called somewhere its result is used, and read only a bare identifier callee. A method is never reached that way, so a log-only catch in a method could not fire at all, and the calls the check did see belonged to whatever free function happened to share the method's name: an identifier caller cannot be attributed to a method. The callee test now follows the declaration, a function or a named arrow bare and a method through `this`, which is the one object a single file resolves and the same restriction Task 4's floating-promise deviation already landed on. The fixtures pin both halves.

- **Task 5, the test-case body is the last function argument after the name (5e91bb1).** Task 2 specified argument one as the callback. Vitest and recent Jest let a case carry an options object between the name and the callback (`test("n", { timeout: 5000 }, fn)`) and a trailing timeout after it (`it("n", fn, 10000)`), so a fixed position read zero assertions for every case of the first form, which is a false positive for any rule that asks whether a case asserts at all. The body is now the last `arrow_function`/`function_expression` among the arguments after argument zero; argument zero is the name and is never the body, so `it(() => {})` stays a case with no body rather than one whose name argument is counted. Pinned by `the_body_is_the_last_function_argument_not_the_second`.

- **Task 3, a base version that parsed with errors records no `previous` entry (1a7389c).** `skipped_at` returned a set unconditionally, so a base revision that failed to parse cleanly contributed the empty set. Tree-sitter recovers from a syntax error by dropping nodes, so an `it.skip` that was in the base version can be missing from the extraction, and asserting the empty set from a recovered tree calls an old skip a new one and also overwrites whatever the index knew about the file. It returns `Option` instead, `None` meaning "this revision has nothing trustworthy to say about the file", and the caller records nothing rather than a wrong entry.

- **Task 8, the value gates the task did not name: a filler floor, a development URI check and a line length cap.** All three came out of writing the must-not-flag fixture and then the corpus run, and all three narrow the rule rather than widen it. (1) Any value carrying under two bits of surprise per character is filler: `pul-000...000`, `xxxx-xxxx` and the nil UUID that half the default configs in the world write are a shape the task's `all one character` clause missed as soon as a provider prefix sat in front of them. (2) A connection string whose host is local, or whose password equals its username, or whose password is one of a dozen compose-file defaults, is not a credential; `postgres://postgres:postgres@localhost:54322/postgres` is in every Supabase repository alive and blocking a build over it would be indefensible on a locked rule. (3) A line over two thousand characters is a generated bundle or an inlined asset, not something a person typed a key into.

- **Task 8, `looks_random` also rejects whitespace, for a corpus false positive.** The first corpus sweep produced exactly one finding: `oauth2Password: "OAuth2 password grant"` in `autoqa`, a label on a form. It is 21 characters, carries all four character classes and scores over four bits per character, so every clause the task specified passed it. No provider generates a credential with a space in it, so the clause is free, and the label is now a clean-fixture line. The second sweep produced zero findings on all five repositories.

- **Task 8, the generic password entry has no leading word boundary, and the rules crate gained `blake3` and `serde_json` alongside `regex` and `base64`.** `(?:password|...)` never matches `dbPassword`, which is how the assignment is actually spelled in a TypeScript repository; the task's own regex has no ``, and the entropy gate is what holds precision here, not the boundary. The two extra dependencies are both already workspace members compiled for `locrin-core`: the anchor is a blake3 prefix of the value and the JWT payload is JSON, and hand-rolling either would have been worse code for no build cost saved.

- **Task 8, the table ships 159 entries rather than 100.** The plan asked for at least a hundred and named about ninety; the rest are the providers the founder's own stack uses (Expo, RevenueCat, OneSignal, AppsFlyer, Branch, Statsig) and the near neighbours of entries already listed. Every one of them has a must-flag and a must-not-flag fixture line, and the fixture test fails if a new entry arrives without them.

- **Task 8, two legacy encrypted PEMs in one file share a finding id (known limitation).** A private key finding is anchored on the material after the header, and for a legacy encrypted PEM that material is the `Proc-Type: 4,ENCRYPTED` line, which is character for character the same in every such key. So two encrypted keys in one file, each with `Proc-Type` on the line after its header, produce one id between them and the second is the first's duplicate. The `DEK-Info` line below it carries an initialisation vector that is unique per key and would separate them; reading it means looking one line further than `key_material` looks today, which is a small change to make deliberately rather than fold into this task. Two encrypted keys in one source file is rare enough that the limitation is recorded rather than fixed here.

- **Task 10, a SQL-family finding inside a test file stands at Medium confidence (review ruling).** The rule's own claim is unchanged and so are its evidence, severity and CWE; only the confidence moves, and only for `CWE-89`. The reason is the corpus: 25 of the rule's 28 findings were jest seeding a fixture database (`mod.__sqlite.exec(`INSERT INTO ... '${ENROLLMENT_ID}'`)`), every one an accurate report of interpolated SQL and every one harmless, against three findings in shipped code. At High they crowd out the two findings with teeth; at Medium they read as the advisory they are. `locrin_core::testcases::is_test_file` is the same test `test-no-assert` and `test-newly-skipped` already use. The code and command families are deliberately untouched: a shell command built in a test script runs on the same machine as one built anywhere else, and `eval` in a test is still `eval`. Pinned by the edge fixture `injection_sink/edge/seed.test.ts`.

- **Task 14, `supabase-service-role-in-client` exempts a file that declares the name as a member of an `interface` or a `type`.** The task's rule was "flag every line containing the identifier" in any file the `server_paths` globs do not cover. The corpus overruled it. `fastlift-admin` is a Cloudflare Worker whose whole source tree is server code and whose entry point sits at `src/worker.ts`, which matches none of the defaults, and all six findings the rule produced there were the two shapes one `export interface Env { SUPABASE_SERVICE_ROLE_KEY: string }` creates: the declaration line itself, and every `env.SUPABASE_SERVICE_ROLE_KEY` read off a parameter of that type. Six of six false, on the only repository in the corpus that produced a finding at all. The exemption is exact rather than a guess at the shape of a line: `property_signature` is the TypeScript grammar's node for an interface or object-type member and nothing else, and a declaration is TypeScript saying the value arrives from the runtime rather than being written down here, which is precisely the claim a bundler exposure would contradict. The token arm is not exempted with it, because a pasted key is an exposure whatever the file's types say. This narrows what the rule reports and never widens it. `framework.server_paths` was not touched, per the task. Pinned by the edge fixture `supabase/edge/src/env.ts` and two unit tests.

- **Task 14, both Supabase rules produce nothing on the corpus and ship on fixture evidence.** Global Constraints: a rule that produces no findings on the corpus is unmeasured and ships on fixture evidence, stated as such. After the tightening above the total across all five repositories is zero, and both zeros were checked rather than assumed. `supabase-service-role-in-client`: FastLift holds 17 files naming `service_role` and every one is under `supabase/functions/**`, exempt by the first default glob, so the zero is 17 correct exemptions and not a rule that never ran; copying one of those files to a client path in a scratch repository reports it at its real line. `supabase-table-without-rls`: FastLift's 35 migrations create 33 tables and enable row-level security on all 33, so the zero is 33 correct answers; deleting one `enable` line in a scratch copy reports that table, by name, at its real `create` line, and says nothing about the other 32. Neither probe wrote into a corpus checkout.

- **Task 10, an `exec` this file cannot place is filed by what it carries, not as SQL by default (review ruling).** Task 10 restricted the command family to the child-process object names and said in its module doc that the cost was "a wrapper module named anything else (`runner.exec`) going unseen". It was not unseen: the `exec` property is in `SQL_PROPERTIES`, so `runner.exec(`rm -rf ${path}`)` was reported as `SQL built from a template with substitutions`, a shell injection filed under CWE-89 with a fix telling the developer to use query placeholders. The receiver now decides in three ways rather than two: a child-process object is a shell, a regular-expression receiver is nothing, and any other object is read off the argument, SQL when the string carries a query word (`select`, `insert`, `update`, ...) or when this file can read no string at all, and a shell command otherwise. `db.exec(`insert into ...`)` and `db.exec(stmt)` therefore stay SQL, which is what the corpus's 25 findings are, and only a command line moves. The alternative, claiming every unplaceable `exec` for the command family, would have relabelled that whole cluster CWE-78.

- **Task 13 (Task 12 review ruling A), `Lockfile.hash` is the hash of the package list rather than of the file text.** The snapshot in `osv_batch` is one JSON document zipped positionally against `lock.packages`, so the key has to promise that the list has not moved under it, and a text hash promised the wrong thing in both directions: a change to the parsers in `lockfile.rs` would have kept the key while the list changed under it, attaching an advisory to the wrong package, and a lockfile edit that touches only a resolved URL or an integrity hash would have thrown away a snapshot whose answer had not changed. The key is now `name@version` per line, sorted, hashed, so the three lockfile formats describing one install share a snapshot and installing a package invalidates it. Pinned by `the_hash_follows_the_package_list_and_not_the_text`.

- **Task 13 (Task 12 review ruling B), an online run reuses a batch snapshot younger than one day without fetching.** One day is already the age at which `osv::check` starts warning the reader that the snapshot is old, so it is the age at which the run should stop trusting it, and below that a run made a request whose answer it would have accepted from cache anyway. A warm run now asks the network nothing at all, which is what makes a graph rule that runs on every `check` affordable in a pre-commit hook; the cost is advisories up to a day stale, which is the staleness the warning threshold already accepted. Offline behaviour is unchanged. Pinned by `an_online_check_over_a_snapshot_from_today_makes_no_request` and `an_online_check_over_a_day_old_snapshot_refreshes_it`; `a_failed_request_falls_back_to_the_snapshot_rather_than_failing_the_run` now backdates its snapshot, because a fresh one no longer puts a request in the way of the answer.

- **Task 13, `run_rules` overwrites a finding's severity only when the config sets one.** `vulnerable-dependency` is the first rule whose severity is a property of the finding rather than of the rule: CRITICAL and HIGH advisories are High, MODERATE is Medium, everything else is Low. `run_rules` assigned `config.severity_for(id, rule.default_severity())` to every finding unconditionally, which would have flattened all three to High. It now assigns `config.severity_override(id)` when the config sets one and leaves the finding alone otherwise, and a locked rule still gets its own default forced on it. For every other rule this is the same behaviour by a different route: `finding_at` already stamps `rule.default_severity()`, which is exactly what `severity_for` returned when the config said nothing. `Config::severity_for` is replaced by `Config::severity_override`, and `a_configured_severity_overrides_every_advisorys_rating` pins that a repository can still flatten the ratings it disagrees with.

- **Task 13, the spec 3.4 benchmarks pass `--offline`.** `vulnerable-dependency` is a graph rule, so it runs on every `scan` and every `check`, and `crates/cli/tests/bench.rs` ran neither with `--offline`. - **Task 15, a cookie flag whose value is neither `true` nor `false` counts as set.** The task said `express-cookie-insecure` reports an options object "lacking `httpOnly: true`", which read literally reports `secure: process.env.NODE_ENV === "production"`: the commonest way a repository writes a cookie that is secure in production and readable over `http://localhost` in development. A flag is therefore missing when it is absent from the object or written `false`, and an options argument the file cannot read at all (`res.cookie(n, v, opts)`) is not an answer and not a finding. That is the same stance the CORS rule takes on `cors(corsOptions)`: the rules report the configuration they can quote. `a_computed_flag_and_an_unreadable_options_object_are_left_alone` pins it.

- **Task 15, the evidence reads the method in upper case.** `{method}` in the task is the property as written (`get`), and the evidence says `GET /admin/users registered without requireAuth`. An HTTP method is upper case everywhere a reader meets one, in a log line and in the specification, and the finding is read by a person.

- **Task 13 (review fix, controller's ruling), a scoped run reports lockfile advisories only when the scope itself names the lockfile, and skips the rule entirely otherwise.** `vulnerable-dependency` is a graph rule and every scoped run filtered graph findings to `wide` (the scope plus its import neighbourhood). The lockfile is not a source file, so it is in no walk, no index and no neighbourhood, and `wide` could never contain it: on every `check <paths>`, `--changed`, `--base` and `--since` the rule ran, read the lockfile, read the snapshot and, online, made its network calls, and then had all of its findings discarded. The run now keeps a raw scope alongside the source-file scope (every path the command line named before the language filter, and for a diff scope git's whole file list before the walked-rels intersection), computes the lockfile's path without parsing it through a new `lockfile::locate`, and when that path is not in the raw scope drops `vulnerable-dependency` from the graph rule list for the run. When it is in the raw scope, its findings are kept whatever `wide` says. Whole-repository runs are unchanged. `--changed` takes its scope from the index, which holds source files only, so it can never name the lockfile and never reports advisories; the rule's module doc states the contract. A directory argument names the walked files under it, so `check src` does not put the lockfile in scope either, which is the same rule read consistently. Pinned end to end in `crates/cli/tests/cli.rs` by `a_scoped_run_reads_the_lockfile_only_when_the_scope_names_it`, entirely offline, through the presence or absence of the rule's own no-snapshot warning on stderr.

- **Task 16, a directory argument puts the lockfile in the raw scope when the lockfile lies under it.** The Task 13 review ruling above closes by reading its own contract as "a directory argument names the walked files under it, so `check src` does not put the lockfile in scope either". Half of that is right and half is a bug: the walk holds source files only, so `check .` named every file in the repository except the one `vulnerable-dependency` reads, and a founder checking the whole repository by naming its root got no advisories at all while the identical `check` with no path did. Pinned by two more legs on `a_scoped_run_reads_the_lockfile_only_when_the_scope_names_it`, which is now seven.

- **Part B fix wave, `vulnerable-dependency` chooses the fixed version by the range that holds the installed version (`d654658`).** Task 13 read "the first version the advisory declares fixed" as the first `fixed` event in the matching npm `affected` entry. An advisory carries one range per maintained branch, each with its own `fixed`, and the document lists them oldest first, so on fasting-app 16 of 54 findings named a version from the wrong branch and five of those named an older release than the one installed: `fast-uri 3.1.5` was told to install `2.4.5`, `@xmldom/xmldom 0.9.10` to install `0.8.15`, `0.8.13` and `0.7.13` to install `0.9.11`, `js-yaml 3.15.1` to install `4.3.2`. - **Task 12, three readings the task did not specify: extra warnings, a short batch response rejected, and npm workspace keys skipped.** (1) The task names two warning strings. The warm gates are not given the allowance: they are the ones a developer feels, and both are green in absolute terms.

- **Tasks 9 to 11, three fixes from the whole-branch review.** Each narrows a rule or corrects a claim, and each has a reproduced case behind it. (1) `unescape` is never a sanitiser. `html-injection` recognises a sanitiser by its callee name containing `sanitize`, `purify`, `escape`, `clean`, `dompurify` or `xss`, and `_.unescape(html)` contains `escape` while doing the exact opposite: it turns `&lt;script&gt;` back into a tag, which is the shape the rule exists to report. A callee containing `unescape` is now never exempt, however it is spelled. (2) `shell: "<string>"` enables a shell. `injection-sink` read the option as `shell: true` only, and Node runs the command line through a shell for `shell: "/bin/sh"` exactly as it does for `true`; a string is how the option is written whenever the shell has to be chosen, so an argv call carrying one was reported as safe. Only a literal is read: `shell: process.env.SHELL` reaches a shell just as surely and this file cannot say so. (3) `weak-crypto`'s identifier scan stops at a class field. The scan climbs to the enclosing statement, and neither a field initialiser nor an object value is a `*_statement` node, so the climb ran past the field, past the class body and out to the `export` in front of the class, then read every name the class declared: one `private password` field made a cache-key hash four fields away read as a credential. `variable_declarator`, `public_field_definition`, `pair` and `class_body` now stop it.

- **Part B fix wave, the raw scope covers every non-source file the scope names, and the graph retain reads it.** The Task 13 and Task 16 rulings above built a raw scope for one file, the lockfile, and left the graph `retain` filtering on the import neighbourhood plus that one path. `supabase-table-without-rls` reports against a `.sql` under `supabase/migrations`, which is in no walk, no index and no neighbourhood either, so every finding it produced on a scoped run was discarded: `check .`, `check supabase`, `check supabase/migrations/0001.sql` and `check --base HEAD` all read the migrations and then reported nothing. The rule was right and the plumbing was wrong, so the plumbing is generalised rather than the lockfile case duplicated. The raw scope of a narrowed run is now every existing file the scope names, source or not: git's whole list for a diff, the files named outright, and for a directory a full listing of the tree beneath it (`walk::all_files`, the same walk `source_files` runs without the language filter on the end, so the excludes and the gitignore still apply). A graph finding survives when the neighbourhood holds its file or the raw scope does, which subsumes the lockfile clause. And, mirroring the lockfile rule's skip, a narrowed run that names no migration drops the RLS rule from the run rather than reading every migration to have its answer discarded. `--changed` still reports neither: that scope is the index's watermark and the index holds source files only, which both rules' module docs now say. The same wave also landed `--offline` on the two baseline commands (they run every rule, `vulnerable-dependency` included), a network-down latch so a failed batch request costs one timeout rather than one per advisory, an unreadable snapshot row treated as absent, `is_safe_id` requiring a letter or a digit so a path segment of dots cannot steer a request, "No fixed version applies to this version" for a finding no advisory range covers, a route-based anchor for a cookie set in an anonymous handler, and `set` read as SQL only when its second word is a database setting.

### Task 4: `swallowed-error`

**Files:** create `crates/rules/src/swallowed_error.rs`, `crates/rules/tests/swallowed_error.rs`, fixtures `crates/rules/tests/fixtures/swallowed_error/{flag,clean,edge}/`; register.

Rule (File scope, Erosion, Medium):
1. **Empty catch** (confidence High): `catch_clause` whose `body` has no named children other than `comment`. Evidence: the trimmed `catch` line. Fix: `Handle the error, rethrow it, or log it with enough context to act on; an empty catch hides failures`.
2. **Log-only catch whose result is used** (confidence Medium): the catch body consists only of expression statements that are `console.<anything>(...)` calls, with no `throw` and no `return`; the enclosing function (nearest `function_declaration`, `method_definition`, or `variable_declarator` with an arrow/function value) has a name, and that name is called elsewhere in the same file in a position whose parent is not an `expression_statement` (its result is used). Evidence: `catch in <name> only logs; callers use its result`. Fix: `Return a failure value or rethrow; a caller that receives undefined cannot tell an error from an empty result`.
3. **Floating promise** (confidence High): an `expression_statement` whose expression is a `call_expression` (possibly wrapped in nothing else) whose callee is an identifier naming a same-file `async` function (`function_declaration` with the `async` keyword, or `variable_declarator` whose value is an `arrow_function`/`function_expression` with `async`), or a member call `this.<name>(...)`/`<obj>.<name>(...)` where `<name>` is a same-file async method or function; and the expression is not `await`-ed, not `void`-ed, and not followed by `.then(`/`.catch(`/`.finally(` in the same expression.
